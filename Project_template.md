# Проектная работа 7 спринта: RAG-бот для QuantumForge Software

## Задание 1. Исследование моделей и инфраструктуры

### Контекст и ограничения кейса

Я делаю решение для внутреннего корпоративного ассистента QuantumForge Software. Основные требования:
1. Быстро отвечать по внутренней техдокументации и регламентам.
2. Не ухудшить контроль над конфиденциальными материалами.
3. Снизить время поиска и повторяющихся вопросов.
4. Иметь понятную стоимость эксплуатации и возможность масштабирования.

Допущения для проектирования:
1. В базе есть чувствительные документы (архитектура, политики, клиентские артефакты).
2. Нагрузка средняя, но растет вместе с объемом документации.
3. Для первого этапа важнее надежность и управляемость, чем максимальная исследовательская гибкость.

### 1) Сравнение LLM: локальные Hugging Face vs облачные OpenAI / YandexGPT

| Критерий | Локальные LLM (HF) | Облачные LLM (OpenAI / YandexGPT) |
|---|---|---|
| Качество ответов | Сильно зависит от модели, квантизации и настройки | Стабильно высокое на сложных вопросах и суммаризации |
| Скорость | Зависит от своего GPU/CPU и очередей | Обычно предсказуемо, упирается в сеть и лимиты API |
| Стоимость владения | Выше входной порог (инфраструктура, MLOps, поддержка) | OPEX по потреблению, проще старт |
| Развертывание | Сложнее: модели, драйверы, мониторинг, обновления | Проще: API и контроль лимитов |
| Безопасность данных | Полный контроль внутри контура | Нужны политики анонимизации и классификация данных |

Вывод: для учебного и пилотного корпоративного RAG быстрее выйти на качество через облачную LLM, но с жесткими правилами по данным.

### 2) Сравнение эмбеддингов: Sentence-Transformers vs OpenAI Embeddings

| Критерий | Sentence-Transformers (локально) | OpenAI Embeddings (облако) |
|---|---|---|
| Скорость индексации | Хорошо масштабируется батчами, зависит от CPU/GPU | Быстро при стабильном канале, ограничено API-квотами |
| Качество поиска | Достаточно для техдоков при правильной модели | Обычно выше стабильность на смешанных доменах |
| Стоимость | Ниже на дистанции при регулярной переиндексации | Оплата за объем текста |
| Конфиденциальность | Текст не покидает контур | Нужна фильтрация и маскирование |

Вывод: для корпоративной базы с регулярным обновлением и требованиями к приватности в базовой конфигурации логичнее локальные эмбеддинги.

### 3) Сравнение векторных БД: FAISS vs ChromaDB

| Критерий | FAISS | ChromaDB |
|---|---|---|
| Поиск и индексация | Очень быстро, зрелая библиотека ANN | Достаточно быстро для типового RAG, зависит от режима хранения |
| Внедрение | Минимальный порог, удобно для PoC | Удобнее как сервис с коллекциями и метаданными |
| Поддержка | Просто в монопроцессе, но больше обвязки вокруг | Удобнее операционно при росте сценариев |
| Стоимость | Минимальная инфраструктура | Выше операционная сложность, но лучше управляемость |

Вывод: для первой сдачи и контролируемого объема данных выбираю FAISS как более простой и быстрый путь к рабочему результату.

### 4) Варианты архитектуры (3-4) и выбор

#### Вариант A. Полностью облачный
- LLM: OpenAI/YandexGPT
- Embeddings: OpenAI
- Vector DB: managed/облачный сервис

Плюсы: лучший time-to-market, минимальный DevOps.
Минусы: риски по данным, постоянные расходы, зависимость от внешнего провайдера.

#### Вариант B. Гибрид 1
- LLM: OpenAI/YandexGPT
- Embeddings: локальные Sentence-Transformers
- Vector DB: FAISS

Плюсы: хороший баланс качества и приватности, быстро внедряется, низкий порог сопровождения.
Минусы: остается внешняя зависимость по генерации ответов.

#### Вариант C. Гибрид 2
- LLM: локальная (HF)
- Embeddings: локальные
- Vector DB: FAISS/ChromaDB

Плюсы: полный контроль данных.
Минусы: выше требования к GPU и MLOps, риск просадки качества ответов на старте.

#### Вариант D. Полностью локальный enterprise-контур
- LLM: локальная production-модель
- Embeddings: локальные
- Vector DB: ChromaDB (как сервис)

Плюсы: соответствие строгим требованиям безопасности и аудита.
Минусы: самый дорогой по внедрению и поддержке, нужен зрелый внутренний ML/Platform контур.

### Рекомендуемая конфигурация сервера

Для выбранного варианта B (пилот/учебная сдача, но с реалистичным корпоративным подходом):
1. CPU: 8 vCPU
2. RAM: 32 GB
3. Disk: NVMe SSD 200 GB
4. GPU: не обязателен на старте (при CPU-инференсе эмбеддингов); опционально 1x GPU уровня L4/A10 для ускорения индексации

### Итоговая рекомендация для QuantumForge

Рекомендую вариант B (гибрид 1):
1. LLM в облаке дает предсказуемо высокое качество ответов и быстрый запуск.
2. Локальные эмбеддинги снижают риски по конфиденциальным данным и стоимость переиндексации.
3. FAISS закрывает задачу первого этапа с минимальной операционной сложностью.
4. Архитектура масштабируется: при ужесточении требований можно перейти к локальной LLM без полной переделки пайплайна.

Итого по векторной БД: выбираю FAISS как оптимум для текущего объема, скорости запуска и стоимости сопровождения на этапе проектной работы.
